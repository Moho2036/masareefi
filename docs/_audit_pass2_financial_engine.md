## أولاً: المعادلات والقواعد الخاطئة أو القديمة في القسم (3) من البايبل

### 1. استقراء المصاريف المتوقعة (Adaptive Extrapolation vs Linear Extrapolation)
* **ما يقوله البايبل (الأسطر 540-547):**  
  يذكر البايبل أن المصاريف المتوقعة لبقية الشهر تُحسب عبر ضرب معدل الصرف اليومي الفعلي في الأيام المتبقية:  
  $$\text{projectedRemainingExpense} = \text{actualDailySpendFils} \times \text{futureUnelapsedDays}$$
* **ما يفعله الكود الفعلي (`src/lib/forecast.ts` الأسطر 453-463):**  
  الكود يطبق **نموذج تنعيم متكيف (Adaptive Weighting Model)** في الأيام الخمسة الأولى من الدورة المالية (`elapsedDays < 5`). إذا تجاوز معدل الصرف اليومي الفعلي الميزانية اليومية الأساسية المفترضة (`baselineDailyBudgetFils`)، لا يعتمد الكود على الصرف الفعلي وحده حتى لا يُحدث قفزات تشاؤمية كاذبة، بل يدمج المعدلين تدريجياً حسب وزن الأيام المنقضية:
  ```typescript
  // src/lib/forecast.ts L455-463
  let effectiveDailySpendFils = actualDailySpendFils;
  if (elapsedDays < 5 && baselineDailyBudgetFils > 0 && actualDailySpendFils > baselineDailyBudgetFils) {
    const weight = elapsedDays / 5;
    effectiveDailySpendFils = Math.round(
      (weight * actualDailySpendFils) + ((1 - weight) * baselineDailyBudgetFils)
    );
  }
  ```
  هذا التدرج المتكيف يحمي التوقع من التشوّه عند دفع فاتورة كبيرة في اليوم الأول أو الثاني من الشهر، وهو غير موثق إطلاقاً في البايبل.

### 2. تدفق رصيد الترحيل في الأشهر المستقبلية (Future Month Intermediate Roll-Forward)
* **ما يقوله البايبل (الأسطر 500-515):**  
  يشير البايبل إلى أن التوقع المالي للأشهر المستقبلية يعتمد على رصيد ترحيلي ثابت مستلم من `usePeriodRollover`.
* **ما يفعله الكود الفعلي (`src/lib/forecast.ts` الأسطر 388-390):**  
  إذا كانت الفترة المعروضة شهراً مستقبلياً (`isFutureMonth = true`)، فإن `forecast.ts` يحسب تلقائياً كافة الالتزامات المتكررة وأقساط الديون التي ستقع بين تاريخ اليوم (`today`) وبداية ذلك الشهر المستقبلي (`range.start`) ويخصمها من الرصيد المرحل:
  ```typescript
  // src/lib/forecast.ts L388-390
  const adjustedRollover = rolloverBalanceFils !== undefined
    ? rolloverBalanceFils + intermediateRecurringNet - intermediateDebtObligations
    : undefined;
  ```
  بدون هذا التعديل، كان التوقع المستقبلي سيتجاهل الالتزامات الحتمية الواقعة في الأشهر البينية، مما يعطي رصيداً مستقبلياً وهمياً.

### 3. حساب يوم العجز المتوقع وتخفيض الصرف الموصى به
* **ما يقوله البايبل (الأسطر 538-555):**  
  يذكر البايبل مؤشرات الصحة المالية (`safe`, `warning`, `danger`) وصافي التوقع الإجمالي فقط.
* **ما يفعله الكود الفعلي (`src/lib/forecast.ts` الأسطر 496-506):**  
  يحسب الكود مقياسين رياضيين حرجين إضافيين:
  1. **يوم العجز المتوقع (`estimatedDeficitDay`):** إذا كان الرصيد الحر أقل من المصاريف المتوقعة المتبقية، يُحدد الكود بالضبط رقم اليوم في الشهر الذي سينفد فيه الرصيد بالكامل:
     $$\text{estimatedDeficitDay} = \text{elapsedDays} + \lfloor \text{freeBalance} / \text{effectiveDailySpendFils} \rfloor$$
  2. **مبلغ التخفيض اليومي الموصى به (`recommendedDailyReductionFils`):**
     $$\text{recommendedDailyReductionFils} = \lceil \text{deficitAmount} / \text{remainingDays} \rceil$$
  هذه المؤشرات تُعرض للمستخدم في بطاقة التوقع المالي لتزويده بإرشاد علاجي فوري وليس مجرد تنبيه عام.

### 5. مقام حساب متوسط الإنفاق في التقرير السنوي (Annual Divisor Rule)
* **ما يقوله البايبل (الأسطر 560-565):**  
  يفترض قسمة إجمالي مصاريف السنة على عدد الأشهر المنقضية حتى اليوم.
* **ما يفعله الكود الفعلي (`src/lib/reports.ts` الأسطر 145-147):**  
  المقام لا يعتمد على عدد الأشهر الزمنية المنقضية، بل يعتمد حصرياً على **عدد الأشهر التي سُجلت فيها مصاريف فعلية** أكبر من الصفر (`monthsWithExpense`):
  ```typescript
  // src/lib/reports.ts L145-147
  const monthsWithExpense = monthlySummaries.filter(m => m.expenseFils > 0).length;
  const averageMonthlyExpenseFils = monthsWithExpense > 0
    ? Math.round(totalExpenseFils / monthsWithExpense)
    : 0;
  ```
  هذا يمنع هبوط المتوسط بشكل مضلل للمستخدم الجديد الذي انضم للتطبيق في شهر أغسطس أو المستخدم الذي لم يسجل أي مصاريف في بعض الأشهر.

* **ما يقوله البايبل (الأسطر 600-608):**

## ثانياً: المعادلات والمنطق المالي الموجود في الكود وغير مذكور في البايبل

### 1. التعريف الحركي لـ "الميزانية" في محرك التنبيهات (`notifications.ts`)
* **الواقع البرمجي:** لا توجد مجموعة بيانات في Firestore باسم `budgets`.
* **المعادلة المطبقة (`src/lib/notifications.ts` الأسطر 242-264):**  
  تُعرّف "الميزانية المتاحة" ديناميكياً بأنها **إجمالي السيولة الحالية للشهر**:
  $$\text{totalLiquidityFils} = \text{currentMonthIncomeFils} + (\text{rolloverEnabled} \ ?\ \text{priorBalanceFils} : 0)$$
  - إذا تجاوز إجمالي المصاريف قيمة `totalLiquidityFils` (مع وجود دخل أو رصيد مرحل): يُطلق تنبيه عجز الميزانية الحرج (`budget_deficit_${fiscalMonthKey}`).
  - إذا بلغت المصاريف $\ge 80\%$ من السيولة المتاحة: يُطلق تنبيه اقتراب نفاد الميزانية (`budget_warning_80_${fiscalMonthKey}`)، ويتحول إلى عاجل (`isUrgent: true`) إذا تجاوزت النسبة $90\%$.

### 2. تخطي الأقساط اليدوية عبر `paymentsByMonth` في المعاملات المتكررة
* **الملفات:** `src/lib/recurring.ts` (الأسطر 141-143)، `src/hooks/useRecurringProcessor.ts` (الأسطر 67-73).
* **المنطق:** المعاملة المتكررة المرتبطة بجمعية (`circleId`) أو التزام شهري تحتوي على قاموس `paymentsByMonth: Record<string, boolean>`. إذا قام المستخدم بإلغاء سداد قسط لشهر معين يدوياً (`paymentsByMonth[monthKey] === false`)، فإن معالج التكرار يتخطى توليد تلك المعاملة نهائياً حتى لو كان تاريخ الشهر مستحقاً، مما يمنع إعادة خصم القسط قسرياً.

### 3. أفق الالتزامات الوشيكة في مطلع الدورة المالية التالية (Next Cycle 3-Day Horizon)

* **المنطق:** يحسب المحرك مجموع المصاريف المتكررة وأقساط الديون المستحقة خلال أول 3 أيام من الشهر المالي القادم:
  ```typescript
  // src/lib/forecast.ts L374-383
  ```

### 4. معالجة المعاملات ذات التاريخ المستقبلي في الشهر الجاري (Future-Dated Discretionary Exclusion)
* **الملف:** `src/lib/forecast.ts` (الأسطر 442-446).
* **المنطق:** عند حساب معدل الصرف اليومي الفعلي (`actualDailySpendFils`) للأيام المنقضية، يستبعد المحرك أي معاملة مسجلة بتاريخ مستقبلي (مثلاً معاملة تم تقييدها مقدماً بتاريخ غدٍ أو بعد غد):
  ```typescript
  // src/lib/forecast.ts L444
  if (txDate > today) return false;
  ```
  هذا يضمن أن معدل الصرف اليومي للأيام الماضية يمثل الصرف الحقيقي فقط ولا يقسم مبالغ مستقبلية على أيام ماضية.

### 5. حماية وتطبيع نسب توزيع التصنيفات (Category Distribution Rounding Guard)
* **الملف:** `src/lib/aggregate.ts` (الأسطر 60-75).
* **المنطق:** عند تقريب نسب الإنفاق لكل تصنيف إلى منزلة عشرية واحدة، يمنع الكود وصول أي تصنيف فردي إلى $100.0\%$ إذا لم يكن المصروف الوحيد (يُقيد عند $99.9\%$)، كما يضمن ألا يتجاوز مجموع النسب $100.0\%$ عبر تعديل الفائض من التصنيف الأكبر:

### 6. تقييد نسبة الادخار المحسوبة (Savings Rate Clamping)
* **الملف:** `src/lib/reports.ts` (الأسطر 167-172).
* **المنطق:** تقيد نسبة الادخار بين $-100\%$ و $+100\%$:
  $$\text{savingsRate} = \max(-100, \min(100, \text{round}(((\text{income} - \text{expense}) / \text{income}) \times 100)))$$
  إذا كان الدخل صفراً، تُعاد النسبة $0\%$ مباشرة لتجنب القسمة على صفر.

### 7. حصص الجمعيات العائلية ونظام الصرف الصافي (Money Circles Shares & Net Payout)
* **الملف:** `src/services/moneyCircles/circleCalculations.ts` (الأسطر 15-45).

### 8. خوارزمية التسوية الفورية للمحفظة (Instant Wallet Reconciliation Algorithm)
* **الملف:** `src/lib/reconciliation.ts` (الأسطر 27-77).
* **المنطق:**
  1. تبحث الدالة أولاً عن أي معاملات تسوية سابقة تحمل العنوان المخصص `"تسوية رصيد المحفظة"` وتحذفها من إجمالي المعاملات لضبط الأساس المحاسبي الحقيقي.
  2. تحسب الفارق: $\text{diffFils} = \text{targetBalanceFils} - \text{currentNetFils}$.
  3. إذا كان $\text{diffFils} \ge 0$: يتم تحديث الرصيد الافتتاحي في الإعدادات مباشرة `openingBalanceFils = diffFils`، دون إنشاء أي معاملة مصطنعة، مع ضبط `rolloverBalance = true` و `rolloverStartDate = null`.
  4. إذا كان $\text{diffFils} < 0$: يُضبط `openingBalanceFils = 0` وتُنشأ معاملة مصروف تصحيحية بقيمة العجز تحت تصنيف `"أخرى"` لإعادة توازن المحفظة.

## ثالثاً: خريطة التأثير المتسلسل الكاملة (Master Cascading Impact Matrix)

توضح هذه المصفوفة الهندسية تدفق البيانات الدقيق لكل عملية في النظام، وما يتم تحديثه في Firestore وذاكرة التطبيق والتخزين المؤقت، وما يتم حمايته من التغيير:

| الإجراء (User Action) | التحديث في Firestore | التحديث في الذاكرة / LocalStorage | التأثير على التوقع والمؤشرات | الكيانات المحمية من التعديل (Shielded) |
| :--- | :--- | :--- | :--- | :--- |
| **إضافة معاملة يدوية** (`addTransaction`) | إضافة وثيقة في `transactions` عبر `commitFirestoreWrite`. | تحديث `AppDataContext`، وتحديث كاش `masareefi_category_usage` لترتيب الأكثر استخداماً. | إعادة حساب `monthNet`، تحديث `actualDailySpendFils`، وفحص فوري لتنبيهات 80% والعجز. | لا تُمس المعاملات المتكررة أو الديون. |
| **تعديل معاملة** (`updateTransaction`) | تحديث وثيقة المعاملة في `transactions`. | استبدال فوري في كاش `AppDataContext`. | إذا تغيّر التاريخ أو المبلغ: يُنقل الأثر بين الأشهر المالية، ويُعاد احتساب التوقع المالي للشهرين. | حقول الربط بالديون والجمعيات تظل متطابقة ما لم يُعدل نوع المعاملة. |
| **حذف معاملة** (`deleteTransaction`) | حذف الوثيقة من `transactions`. | إزالة المعاملة من `AppDataContext`. | استرجاع السيولة فوراً، وتحديث متوسط الصرف اليومي. | لا تُحذف سجلات الديون أو الجمعيات الأصلية، بل تُلغى الدفعة المقترنة فقط إذا كانت دفعة دين. |
| **إنشاء دين جديد مع سلفة أولى** (`addDebt`) | دفعة ذرية (`writeBatch`): وثيقة `debts` + وثيقة فرعية `entries/entry_{id}` + وثيقة في `transactions` (`debt_init_{debtId}`) إذا طُلب الربط. | تحديث مصفوفة `debts` و `transactions` في `AppDataContext`. | يؤثر على الرصيد المتاح فوراً إذا كان الربط مفعلاً (كمصروف لـ `i_lent` أو دخل لـ `i_borrowed`). | لا تتأثر الديون الأخرى لنفس الشخص. |
| **إضافة سلفة جديدة لدين قائم** (`addDebtEntry`) | دفعة ذرية: تحديث `totalFils` في `debts` + إضافة وثيقة في `entries` + إضافة معاملة (`debt_entry_{entryId}`). | تحديث كائن الدين في `AppDataContext`. | زيادة الالتزام، وإعادة فتح الدين إذا كان مسدداً (`settled = false`). | سجلات الدفعات السابقة لا تتأثر. |
| **تسجيل دفعة سداد دين** (`addDebtPayment`) | دفعة ذرية: زيادة `paidFils` في `debts` + تحديث `settled` + إضافة وثيقة في `payments` + إضافة معاملة (`debt_pay_{paymentId}`). | تحديث الدين والمعاملات في `AppDataContext`. | تحديث الالتزامات المستقبلية المتبقية في `forecast.ts` (`upcomingDebtObligations`). | السلف السابقة تظل كما هي. |
| **حذف دفعة سداد دين** (`deleteDebtPayment`) | دفعة ذرية: إنقاص `paidFils` + تحديث `settled = false` + حذف وثيقة السداد من `payments` + حذف المعاملة المرتبطة بها (`debt_pay_{paymentId}`). | تحديث متزامن لكائن الدين ومصفوفة المعاملات. | عودة الدين كالتزام مستقبلي نشط في التوقع المالي. | باقي دفعات السداد تظل سليمة. |
| **ضغط دفعات الدين** (`compactDebtPayments`) | حذف جميع وثائق `payments` الفردية وإنشاء دفعة واحدة مجمعة بمجموع المبالغ وتحديث المعاملات. | تحديث كائن الدين وسجل الدفعات. | المجموع المالي لا يتغير؛ تقليل عدد الوثائق فقط لتسريع القراءة. | لا يتغير `totalFils` أو تاريخ استحقاق الدين. |

## رابعاً: قائمة الحالات الاستثنائية الصعبة (Financial Edge Cases)

### 1. معالجة العجز المرحّل السالب في الصرف اليومي الآمن
* **الحالة:** المستخدم لديه عجز مرحل من الأشهر السابقة بقيمة $-150$ دينار، ودخل الشهر الحالي $200$ دينار (صافي السيولة المتاحة $= 50$ دينار فقط).
* **المعالجة البرمجية (`src/lib/forecast.ts` الأسطر 398-403):**  
  يمنع الكود استخدام `Math.max(0, rollover)`؛ بل يدمج العجز السالب كاملاً ضمن السيولة:
  $$\text{availableBalance} = \text{rolloverBalance} + \text{monthNet}$$
  وبالتالي يتم تقسيم الـ $50$ دينار الحقيقية المتبقية فقط على الأيام القادمة، مما يحمي المستخدم من وهم امتلاك $200$ دينار كاملة للصرف.

---

### 2. السنوات الكبيسة وتعديل نهاية شهر فبراير (Leap Year Clamping)
* **الحالة:** ضبط `monthStartDay = 31` أو `28` في شهر فبراير أو الأشهر ذات الـ 30 يوماً.
* **المعالجة البرمجية (`src/lib/dates.ts` الأسطر 54-80):**  
  تستخدم دوال التواريخ `createUtcSafeDate` وتثبت الساعة عند `12:00:00` لمنع انزياح التوقيت الصيفي/الشتوي (DST)، ويتم تقييد الأيام التي تتجاوز آخر يوم في الشهر إلى الحد الأقصى للشهر (`Math.min(targetDay, daysInMonth)`). وعند الانتقال للشهر التالي الذي يحتوي على 31 يوماً، يستعيد اليوم أصله تلقائياً.

---

### 3. فترة السماح في مطلع الشهر ضد التنبيه الكاذب بالعجز (Grace Period)
* **الحالة:** أول يومين من الشهر المالي (`elapsedDays < 3`)، قام المستخدم بصرف $30$ دينار قبل نزول راتبه الشهري، فأصبح الرصيد سالباً مؤقتاً.
* **المعالجة البرمجية (`src/lib/forecast.ts` الأسطر 523-527):**  
  لا يضع المحرك حالة الشهر في وضع الخطر الأحمر (`danger`)، بل يصنفها كـ تحذير أصفر (`warning`) مع تنبيه توضيحي بأن الشهر بدأ للتو مع وجود مصاريف متوقعة أو دخل متوقع لم يُقيد بعد، مما يمنع إحباط المستخدم في أول أيام الدورة.

---

### 4. تغطية العجز اللحظي عبر دخل متكرر قادم (Liquidity Dip Protection)
* **الحالة:** الرصيد اللحظي الحالي سالب (`availableBalance < 0`)، ولكن هناك راتب شهري متكرر أو دفعة جمعية قادمة مؤكدة قبل نهاية الدورة المالية بمبلغ يغطي العجز وزيادة (`freeBalance > 0`).
* **المعالجة البرمجية (`src/lib/forecast.ts` الأسطر 529-532):**  
  يُصنف المحرك الحالة كـ `warning` وليس `danger`، ويُظهر ملاحظة توضح أن العجز الحالي مؤقت ومغطى بالدخل المتكرر القادم خلال الدورة.

---

### 5. الأشهر الصفرية وتجنب القسمة على صفر في المقارنات
* **الحالة:** حساب نسبة التغير في المصاريف عندما تكون مصاريف الشهر السابق صفراً.
* **المعالجة البرمجية (`src/lib/reports.ts` الأسطر 85-98):**  
  إذا كان أساس المقارنة صفراً، لا تُطبق معادلة النسبة المئوية المباشرة، بل يعيد الكود `null` أو يحدد بوضوح أن القيمة السابقة كانت منعدمة، مما يمنع ظهور قيم `Infinity%` أو `NaN%` في الواجهات.

---

### 6. طوابير العمل دون اتصال بالإنترنت وحماية الحركات (Offline Queueing)
* **الحالة:** انقطاع الإنترنت أثناء إضافة دفعة سداد دين أو تعديل معاملة.
* **المعالجة البرمجية (`src/lib/firestoreOffline.ts` الأسطر 18-35):**  
  تُمرر العمليات عبر دالة الغلاف `commitFirestoreWrite`. إذا فشل الاتصال بقاعدة بيانات Firestore السحابية، تُكتب العملية في الكاش المحلي لـ IndexedDB الخاص بـ Firebase SDK، وتُستكمل الحسابات المحلية في `AppDataContext` فوراً دون تجميد الواجهة أو فقدان الدفعة، ثم تُزامن تلقائياً فور عودة الشبكة.

## خامساً: تناقضات حرجة وثغرات حسابية داخل الكود نفسه (Code Discrepancies)

أثناء التدقيق الجراحي للشيفرة المصدرية، تم اكتشاف **تناقضين حسابيين حرجين** بين الملفات يتطلبان المعالجة لاحقاً:

### 1. تناقض معالجة الرصيد الافتتاحي عند إيقاف الترحيل (`rolloverBalance: false`)
* **موقع التناقض:**
  - في `src/context/AppDataContext.tsx` (الأسطر 347-351):
    ```typescript
    // AppDataContext.tsx
    const priorFils = isRolloverEnabled ? rolloverBalanceFils : 0;
    const finalPriorBalanceFils = priorFils + openingFils;
    ```
    يُلاحظ هنا أنه حتى عندما يكون الترحيل معطلاً (`isRolloverEnabled === false`)، فإن `openingBalanceFils` يُضاف إلى الرصيد المرحل للشهر الجاري!
  - في المقابل، داخل `src/hooks/usePeriodRollover.ts` (السطر 95):
    ```typescript
    // usePeriodRollover.ts
    if (!isRolloverEnabled) {
      return 0; // يُعاد صفر مطلق للأشهر السابقة والمستقبلية!
    }
    ```
  - وفي `src/hooks/useDashboardData.ts` (السطر 78) و `src/hooks/useReportsData.ts`:
    ```typescript
    rolloverBalanceFils: isRolloverEnabled || openingBalanceFils > 0 ? effectiveRollover : undefined
    ```
* **الأثر المحاسبي:**
  إذا عطّل المستخدم خيار "ترحيل الرصيد" وكان لديه رصيد افتتاحي مسجل، فإن لوحة التحكم للشهر الحالي ستعتبر الرصيد الافتتاحي جزءاً من الرصيد المرحل، بينما الأشهر الأخرى في `usePeriodRollover` ستعتبره صفراً، مما يخلق تضارباً في الأرقام بين الشهر الحالي والأشهر الأخرى عند إيقاف الترحيل.
* **الحل الهندسي المقترح:** توحيد الشرط وفق القاعدة المذكورة في الدستور الهندسي: "يدخل الرصيد الافتتاحي حصرياً عندما يكون `rolloverBalance` مفعلاً".

---

### 2. غياب تدقيق سقف المبالغ في الحاسبة الرياضية الداخلية (`mathExpression.ts`)
* **موقع التناقض:**
  - في `firestore.rules` (السطر 32): الحد الأقصى للمبلغ المدخل هو مليار فلس (`amountFils <= 1000000000000`).
  - في `src/lib/mathExpression.ts` (السطر 40): الثابت المعرف للحد الأقصى هو `MAX_EXPRESSION_VALUE = 999_999_999.999`.
* **الأثر:**
  إذا أجرى المستخدم عملية ضرب رياضية داخل حقل المبلغ (مثلاً: `500000000 * 2`)، فإن الحاسبة الرياضية قد تقبل ناتجاً يكسر سقف أمان Firestore فيفشل الحفظ بصمت أو برسالة خطأ غير متوقعة.
* **الحل الهندسي المقترح:** مزامنة سقف `MAX_EXPRESSION_VALUE` ليتطابق تماماً مع قيود `firestore.rules` وتحويله إلى فلس قبل الفحص.
